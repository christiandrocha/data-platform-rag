# ADR-011 — Golden set curation methodology

**Status**: Accepted
**Date**: 2026-09-14

## Context

`docs/golden-set/evaluation_questions.yml` is not test data. It is the measuring
instrument that ADR-004's embedding decision rule, ADR-005's reranker A/B,
ADR-008's CI regression threshold, and all four Section 7 publication gates are
scored against. Every quality claim this project makes traces back to it.

An instrument can fail in a way a test cannot: **a biased golden set does not
produce a wrong number, it produces a confident wrong number**, and nothing
downstream can detect it, because everything downstream trusts it. Three
specific paths to that outcome, all silent:

1. **Vocabulary contamination.** Questions written in the corpus's own phrasing
   inflate dense retrieval scores. Every metric improves. Nothing looks wrong.
2. **A moving ruler.** Editing a question after a baseline is recorded makes the
   runs on either side incomparable. A metric that shifts because the instrument
   changed is indistinguishable from one that shifted because the system did.
3. **Wrong ground truth.** An `expected_answer` containing a claim the corpus
   does not support makes Context Recall permanently unachievable for that
   question — and it presents exactly like a retrieval bug, costing a day of
   debugging the wrong component.

This ADR records the commitments that keep those three closed. It is written
before the 45 remaining questions are authored, deliberately: a methodology
adopted after the fact is a rationalisation.

## Decision

### Commitment 1 — Questions are human-authored. The LLM audits and never writes.

No question text, and no `expected_answer`, is generated by a model. An LLM
participates only as an auditor, through `scripts/audit_questions.py`:

| Aspect | Value |
|--------|-------|
| Model | `claude-opus-5` |
| Trigger | Manual, during curation. Never in CI |
| Input per question | Question, `expected_answer`, and cited source excerpts from a local corpus clone |
| Asks | (a) Would someone who had **not** read this source phrase the question this way? (b) Is every claim in `expected_answer` supported by the quoted text? (c) Which cited source is not actually needed? |
| Output | Advisory report to `.claude/dev/reports/audit-{timestamp}.md`. **It never edits the YAML** |
| Cost | ~2,050 in / ~150 out tokens per question ≈ $0.014/question, ~$0.70 per 50-question pass |

The asymmetry is the whole argument. When an LLM *writes* a question, the failure
is silent and it **improves** the metrics — there is no signal to catch it. When
an LLM *audits*, the failure is a wrong line in a report a human reads. Opus
rather than a cheaper model for the same reason: this is the judgment task the
mechanical checks cannot perform, and $0.55 saved per pass is not a reason to put
a weaker judge on the instrument that validates everything else.

**The auditor's scope includes adversarial questions.** It is not limited to
in-scope grounding. For an `intent: out-of-scope` question it additionally asks:
*does the corpus discuss this topic in different words?* That makes the auditor
the semantic safety net for Layer 2 of the adversarial verification below. Cost
is ~$0.05 per adversarial, run on demand.

This placement is deliberate rather than convenient. Detecting paraphrase is
already this commitment's assigned job; asking the human author to also do it
through hand-written probes would duplicate work the ADR has explicitly
delegated to the model.

**When retreat A3 is invoked, provenance becomes mandatory.** A3 — the
pre-approved pragmatic retreat in which an LLM proposes `architecture` questions
while a human writes everything else — requires a `provenance: human | llm` field
on every question before a single LLM-proposed question is written.
Human-written and LLM-proposed questions are audited separately under Layer 2,
and reported separately in RAGAS.

The point of A3 is to make the bias **measurable**, not to hide it. Without
provenance the two populations are indistinguishable after the fact, and the
retreat silently becomes the thing Commitment 1 exists to prevent. With it, the
delta between human- and LLM-authored Context Recall is a measured number. If
that delta is large, it earns a new known gap here or its own ADR on correction
methodology.

**Human questions are written and committed before the LLM proposes any.** The
reverse order compromises the anti-contamination discipline of this commitment: a
human author who has just read LLM phrasings imports their patterns
unconsciously, and the contamination then reaches the questions this commitment
was meant to keep clean. The ordering constraint is not politeness about who goes
first — it is the only thing preventing A3 from contaminating the human half too.

**Layer 2 output is advisory evidence for a human decision, not consensus.** The
author remains the decision-maker and may disagree with Opus. But disagreement
must be documented in the same dev log entry, with reasoning — in the form
*"Opus flagged X as paraphrastic contamination; author considers X semantically
distinct because Y."*

This makes disagreement explicit and auditable rather than silent. An advisory
signal that can be ignored without trace is not a safety net; it is a formality
that will be skipped under deadline. Writing down *why* the model was overruled
is also the only way a later reader can tell a considered override from an
unread report.

### Commitment 2 — The golden set is an instrument, and it has a change policy.

Once ADR-008 records a baseline, the set is frozen with respect to that baseline.
Any change to a **scored** field invalidates comparisons across the change and
requires a re-baseline:

| Change | Re-baseline? |
|--------|-------------|
| Add or remove a question | Yes |
| Edit `question`, `expected_answer`, or `expected_source_paths` | Yes |
| Edit `intent` | Yes — it changes the distribution and the fallback expectation |
| Add or edit `grounding` / `grounding_verified` | No — evidence, not scored |
| Typo fix that provably does not change meaning | No, but record it in the dev log |

**Mechanism, so this is not an honour system:** every evaluation run records the
git SHA of `evaluation_questions.yml` alongside its scores. Two runs with
different SHAs are not comparable, and the comparison tooling must say so rather
than silently subtract. No new YAML field and no manual version bookkeeping — git
already tracks exactly this.

**Precondition on ADR-008**: ADR-008 (RAGAS regression in CI) depends on
ADR-011's change policy. Any threshold in ADR-008 is only meaningful against a
golden set with a declared change policy. If ADR-011 is superseded, ADR-008's
baseline is invalidated and must be re-established.

### Commitment 3 — Grounding evidence is partial, by design.

Every in-scope question carries `grounding_verified: true`. A `grounding` entry
with a verbatim `quote` is required only for **high-risk claims**, identified by
a two-layer rule:

- **Mechanical floor (deterministic).** Any claim span containing a digit, a
  version string, or an ADR ID (`ADR-\d+`) requires a quote. Enforced by regex in
  the validator. This layer never goes stale: digits and ADR IDs are a genuinely
  closed set.
- **Judgment layer (prompt).** The auditor is additionally instructed to flag
  claims naming a technology or mechanism, with concrete examples in the prompt
  rather than a closed list. The examples, with their grep status against the
  corpus recorded on 2026-09-14:

  | Example | In-corpus | Handling |
  |---------|-----------|----------|
  | `1024` (a number) | 0 files | Clean. Used as-is |
  | `Debezium` (a technology) | 10 files | **Illustrative match** — see below |
  | `Unity Catalog` (a mechanism) | 5 files | **Illustrative match** — see below |
  | `ADR-9999` (an ID) | 0 files | Substituted for `ADR-0029`, which matched 2 files |

**Curation rule — illustrative examples are grepped too.** Illustrative examples
of numbers and mechanisms in this section must be verified via grep against the
corpus. Terms that grep positive must either be substituted or explicitly
annotated as *"illustrative match — auditor should recognise as example, not
target"*.

`Debezium` and `Unity Catalog` carry that annotation rather than being replaced.
Substituting an absent technology would make the example worse pedagogy: the
auditor's job is to flag precisely the mechanisms the corpus does discuss, and an
example drawn from outside the corpus teaches the opposite. An **ID** was treated
differently and substituted, because an ADR ID is a precise token rather than a
category, and a real one risks the auditor anchoring on it as a target.

A closed list of "named mechanisms" was rejected: it would need to enumerate
Kafka, Debezium, Snowpipe, Unity Catalog, Lakeflow, dbt, Dagster and stay current
as the corpora evolve, and a stale list fails silently in the permissive
direction. Run-to-run variance in the judgment layer is tolerable **because the
output is advisory** — a human decides. The mechanical floor exists so the
highest-risk class, numbers, cannot be missed by an unlucky run.

Full clause-by-clause evidence for all 50 questions was also rejected: roughly
135 quote entries, most proving prose that carries no factual risk. Ceremony at
that scale gets abandoned around question 20 and then misreported.

## Operating rules that follow

### Authoring order: seeded, interleaved, and the seed is immutable

Questions are authored in a **seeded shuffle** of `corpus_inventory.yml`,
interleaving the two projects, **seed `20260914`**, recorded in the inventory
file.

**The seed is immutable for the life of a golden set generation.** Re-shuffling
mid-curation destroys the property the seed exists to provide: authoring order
would correlate with the re-shuffle point, which is exactly the bias the seeded
order prevents. A new seed is permitted **only** when a set is rebuilt from
scratch — a new generation — and the new seed is recorded together with the
reason for the rebuild.

If the inventory *grows* mid-curation, new ADRs **append** to the end of the
existing walk order. They are not shuffled into it. Appending is deterministic
and leaves the established order untouched.

Order in inventory sequence was rejected: the last ADRs would systematically
receive the most fatigued questions, and writing one project fully before the
other lets a per-project voice drift into the phrasing.

### Adversarial questions are verified absent, never assumed

Every candidate out-of-scope question is grepped against the in-corpus files of
both repos (`docs/adr/`, `README.md`, `contracts/`, `macros/`) before entering
the set. This rule exists because the repo's own suggested example failed it:
"What did Christian decide about Delta Live Tables?" is discussed in two
`sdd-kafka-databricks` ADRs as a rejected alternative, making it a legitimate
`decision` question. DLT is the former name of Lakeflow Declarative Pipelines —
an adversarial chosen by intuition about a rebrand looks absent and is not.

As an adversarial it would have failed `fallback_accuracy` on every run, and
Section 7 requires that metric at 100%.

Each out-of-scope question records `grep_verified: <date>` so the check is
durable rather than a one-time act of diligence.

Every out-of-scope question declares `contamination_probes: list[str]`: the exact
phrases that, if present in the corpus, would cost the question its adversarial
status. The validator requires at least one; two or more is the curation
recommendation, since one probe is usually just the question's subject noun.

The grep is **scoped to the indexed file set** (`docs/adr/`, `README.md`,
`contracts/`, `macros/`), never the clone root, and **case-sensitive**. Both were
decided on evidence: probe `Flink` matches 5 files in the `sdd-kafka-databricks`
clone and 0 in-corpus (all five are `.claude/` internals that are never indexed);
and `sdd-kafka-databricks/README.md:31` reads "Kafka streams, MongoDB documents"
— generic lowercase prose that a case-insensitive probe for "Kafka Streams" would
match, failing q005 over an unrelated phrase.

### Worked examples — what each layer actually catches

**Layer 1 earning its place (verified).** An adversarial about Delta Live Tables
would declare the probe `"Delta Live Tables"`. That probe matches
`sdd-kafka-databricks/README.md:310` ("Databricks Delta Live Tables (DLT)
migration"), an indexed file. Layer 1 fires, the question is rejected before any
model is invoked, and the cost is milliseconds. This is the case the repo's own
README originally proposed as a model adversarial — the cheap layer catches it
outright.

**Why Layer 1 is nevertheless not sufficient.** DLT is the former name of
Lakeflow Declarative Pipelines. This corpus happens to use *both* names — the old
one at `README.md:310`, the new one at `docs/adr/006_lakeflow_migration.md:1` —
so probing either catches it. That is luck, not design. Had the corpus used only
the new name while the author probed the old one, Layer 1 would have been blind
to a topic the corpus discusses at length. A rebrand is precisely the class of
contamination a literal matcher cannot see, and it is why Layer 2 exists rather
than being an optional extra.

**Layer 2 catching what Layer 1 cannot (constructed).**

> Author declares the probe `"Debezium catches up"`.
> The corpus says `"Debezium is still catching up"`.
> **Layer 1 passes** — the literal grep is negative.
> **Layer 2 catches it** — Opus recognises the paraphrase.
> The human decides whether to substitute the question.

*(Constructed, not drawn from the corpus. Grep-verified 2026-09-14: "Debezium
catches up", "Debezium is still catching up", "catching up" and "catches up" all
return 0 in-corpus matches, so the example is safe to use as an example, per the
illustrative-examples rule in Commitment 3.)*

### Recovery workflow — when Layer 1 fails a run

A red gate has two possible causes, and conflating them is how Layer 1 becomes
theatre: an author who treats every failure as a bad probe will widen and narrow
probes until nothing matches, leaving a gate that passes by construction.

**Scenario A — the contamination is real.** The question has lost its adversarial
status; the corpus can answer it.

- The author substitutes the question, or re-classifies its `intent` to whatever
  the corpus actually supports.
- The commit message references the Layer 1 output that triggered the failure.
- Probes for the new or re-classified question are written from scratch. They are
  never inherited from the question that failed.

**Scenario B — the probe was too broad.** The question is still adversarial; the
probe over-captures.

- The author runs `make audit-adversarials q=<id>` — the Layer 2 Opus audit.
- The Opus output is attached **verbatim** to a dev log entry.
- If Opus confirms the probe over-captures → adjust the probe; the commit
  references that dev log entry.
- If Opus instead finds semantic contamination → this was Scenario A. Restart
  there.

**Narrowing a probe is never a unilateral act.** Scenario B requires a Layer 2
run and a dev log entry before the probe changes. That is the structural defence
against quietly editing probes until the gate stops firing: the cheap path out of
a red build costs a model call and a written record, which is more expensive than
fixing the question honestly.

### Re-verification before every eval — a blocking gate, scoped to adversarials

A grep verifies absence *at a point in time*. If a corpus repo later gains an ADR
mentioning Flink, q005 becomes silently invalid: it starts failing
`fallback_accuracy` with no indication that the question, not the system, is what
broke.

**`scripts/verify_adversarials.py` runs as a precondition of every evaluation
run, and a positive match fails the run.** Not a warning.

This follows the severity convention the corpus itself established in
`sdd-kafka-snowflake-2` ADR-0027: *"a dbt test is `error` if the violation,
propagated, would make a business metric objectively wrong."* A contaminated
adversarial, propagated, does not degrade `fallback_accuracy` — it makes it
objectively wrong, while leaving it looking healthy. That is the `error`
criterion, not the `warn` criterion. A warning that does not block is
incompatible with the premise that silent contamination invalidates the measure.

**Scope is deliberately narrow: `intent: out-of-scope` questions only.** A new
corpus mention of a term used by an in-scope question is not a defect — it is
more material available to retrieve. Only for an adversarial does a new mention
constitute a change of semantic status, from "unanswerable" to "answerable".
Narrowing the gate to that category keeps the blocking surface confined to where
the failure logic is falsifiable.

**Precondition on ADR-008**: ADR-008 invokes `verify_adversarials.py` as a
precondition of `make eval` and `make eval-ci`, and treats a non-zero exit as a
failed run. This is a decision taken here, not a question deferred to ADR-008 —
the evidence needed to decide it is already available.

## Consequences

**Positive**:
- The three silent failure modes each have either a mechanical gate or a recorded
  rule, rather than an intention.
- Both preconditions on ADR-008 are explicit, so a future contributor cannot
  calibrate a regression threshold against an undeclared or decayed instrument.
- Curation cost is bounded and known: ~$3.50 of audit across five passes.

**Negative / accepted trade-offs**:
- **45 human-authored questions is the long pole of this feature**, measured in
  days. That cost is accepted as the price of an instrument worth trusting.
- The judgment layer of Commitment 3 is non-deterministic. Accepted because the
  output is advisory and the high-risk class has a deterministic floor beneath it.
- **The blocking re-verification gate requires a corpus clone at eval time.**
  Evaluation otherwise queries only Postgres and needs no clone, so this adds a
  clone step to CI that did not previously exist. Accepted: the alternative is
  scoring against an instrument whose validity is unverified.
- A corpus repo gaining an ADR can now fail an eval run that would previously
  have passed. That is the intended behaviour — the run *should* fail, because
  its result would have been wrong — but it means eval can break without any
  change to this repository.
- `corpus_inventory.yml` is hand-maintained and will go stale if the corpora gain
  an ADR. Mitigated by a check during `corpus-indexing` BUILD, when a clone is
  present. Recorded, not solved.
- The change policy makes the golden set expensive to improve after baselining.
  This is intended — an instrument that is cheap to adjust is not an instrument.

## Alternatives considered

- **LLM proposes questions, human validates.** Rejected: fast and systematic, but
  produces source-mirroring phrasing whose effect is invisible in every metric.
  The bias favours the system being measured.
- **Hybrid by band** — human writes comparison and adversarial questions, LLM
  proposes architecture ones. Rejected for now, but **pre-approved as a pragmatic
  retreat** if authoring at this rigour proves unworkable in reasonable time.
  Condition: add a `provenance` field first, so the two classes stay separable in
  later analysis.
- **Closed list for named mechanisms (deterministic).** Rejected — see
  Commitment 3. Defensible, but fails silently in the permissive direction as the
  corpora evolve.
- **Re-verification as a non-blocking warning.** Rejected. It was the initial
  proposal in DESIGN, and it contradicts this ADR's own premise: if silent
  contamination invalidates the measurement, a signal that permits the run to
  continue is the wrong severity. ADR-0027's consequence-based criterion settles
  it.
- **Re-verification across all 50 questions rather than the 5 adversarials.**
  Rejected: a new corpus mention only changes semantic status for an out-of-scope
  question. Applying the gate broadly would block on changes that are not defects.
- **No change policy; treat the set as editable.** Rejected: it makes ADR-008's
  regression gate meaningless without announcing that it has.
